# 3. 좌표 변환과 월드 메모리

> [← 이전](02_입력_형식.md) · [index](index.md) · [다음 →](04_RTL_구조.md)

---

픽셀 좌표 이벤트를 월드 좌표로 옮겨 월드 메모리에 세는 연산을 정수 단위까지 정한다. RTL은 이 장과 비트
단위로 같아야 하고, 기준 구현은 `software/golden_develop/golden.py`다. 값을 이렇게 정한 근거와 측정은
[설계 근거 2절](../reports/01_설계_근거.md#2-회전-중심과-회전각-추적)에 있다.

## 3.1 모형

### 좌표를 옮기는 세 단계

이 장의 계산은 한 이벤트에 다음 세 일을 한다.

1. **회전 중심을 뺀다.** 화면 좌표를 “회전 중심에서 얼마나 떨어졌나”로 바꾼다.
2. **그 차이를 회전시킨다.** 카메라 때문에 돌아 보인 방향을 되돌린다.
3. **월드 중심을 더한다.** 음수도 가능한 좌표를 메모리 지도 안으로 옮긴다. 그다음 어느 격자 칸에 드는지 구한다.

회전 중심을 빼는 이유는 물체를 화면 왼쪽 위 모서리 주위로 돌리지 않기 위해서다. 월드 중심을 더하는 이유는
회전 중심의 왼쪽 · 위쪽에 있는 점도 음수 주소 없이 저장하려는 것이다.

| 기호 | 뜻 | 구분해야 할 점 |
|---|---|---|
| `p = (x, y)` | 센서에서 읽은 이벤트 픽셀 위치 | 프레임이 바뀌면 같은 물체도 위치가 바뀐다 |
| `c = (cx, cy)` | 영상에서 잡은 회전 중심 | 센서 화면의 정중앙과 같을 필요가 없다 |
| `θ_f` | f번째 프레임에서 영상이 돌아간 각도 | SW 추적 결과 |
| `α` | 누적 지도에서 막대를 수직으로 세우기 위한 전체 방향 보정 | 프레임마다 바뀌는 값이 아니다 |
| `ψ_f` | 이 프레임 좌표에 실제로 적용할 보정 각도 | `α − θ_f` |
| `WC` | 월드 메모리의 중심 위치 | x · y 양쪽에 같은 값을 더한다 |

### 이번 설계가 쓰는 회전 모형

주 대상 녹화의 센서는 광축과 나란한 회전축 둘레를 돈다([설계 근거 1절](../reports/01_설계_근거.md#1-입력-해석)). 그래서 프레임 f의 이벤트
좌표 p를 월드 좌표 w로 옮기는 일은 영상 평면의 2차원 회전 하나다.

    w = R(ψ_f) · (p − c) + WC
    R(ψ) = [[cos ψ, −sin ψ], [sin ψ, cos ψ]]     x 오른쪽, y 아래. ψ가 양수면 화면에서 시계 방향

c는 영상의 회전 중심이고 WC는 월드 메모리 한가운데다. MGROUP은 한 프레임의 이벤트가 시각 하나를 나눠
쓰므로([2장 2.3절](02_입력_형식.md#23-프레임과-시각)) ψ_f도 프레임마다 하나이고, 프레임 안의 이벤트는 모두 같은
각도로 옮긴다.

ψ_f와 c는 SW가 녹화에서 추정해 RTL에 넣는다. 실제 시스템에서는 자이로 등의 측정값을 각도와 위상으로 바꾸는
외부 처리가 이 입력을 공급할 수 있다. ψ_f는 영상이 돈
각도 θ_f를 되돌리고 막대가 수직이 되게 α만큼 더 돌린 값이다(ψ_f = α − θ_f).

센서가 회전축에서 비켜 있어서 회전 중심은 물체 깊이마다 다르다. 회전 하나로는 한 깊이만 맞출 수 있으므로
c는 막대 4개에 맞춘 값을 쓰고, 막대보다 먼 배경은 누적하면 조금 번진다. 렌즈 왜곡은 보정하지 않는다.
장면 1 데이터에서는 일관된 방사 왜곡이 드러나지 않고 보정하면 누적이 오히려 나빠진다([설계 근거 3절](../reports/01_설계_근거.md#3-렌즈-보정)).
이 판단은 roll에 한한다. yaw(9/15 녹화)에서는 물체가 영상 가운데에서 가장자리로 옮겨 가며 배럴 왜곡이 그대로 드러나,
데이터에서 추정한 렌즈 모형(초점거리와 방사 왜곡)을 넣어야 같은 물체가 같은 칸에 쌓인다([설계 근거 10.2절](../reports/01_설계_근거.md#102-915-녹화-수평-회전)).
같은 실험에서 ψ_f를 추적할 때 쓰는 회전 중심이 막대 기울기를 바꾸는 것도 확인했다. 최종 장면 1의 ψ_f는
막대 중심으로 추적한 값이다. **각도를 추적하는 중심**과 **좌표를 옮길 때 빼는 중심**은 역할이 다르며,
최종 장면 1에서는 둘 다 막대 기준 중심으로 맞췄다(3.5절).

## 3.2 프레임마다: 위상과 cos · sin

### 각도를 정수로 보내는 이유

회로는 소수점이 붙은 각도 문자열을 받지 않는다. 한 바퀴를 같은 간격으로 나눈 정수 번호를 받는다.
이 번호가 **위상(phase)**이다. 시계 둘레에 눈금을 붙인다고 생각하면 된다. 한 바퀴를 돌아 같은 방향으로
오면 번호도 처음으로 돌아간다. **LSB**는 이 표현에서 가장 작은 한 눈금이다.

ψ_f는 16비트 위상 φ로 넣는다. 2^16이 360°이고 1 LSB는 0.0055°다.

    φ = round(ψ / 360° × 65536) mod 65536

예를 들어 위상 0은 0°, 16,384는 90°, 32,768은 180°, 49,152는 270°다. 음수 각도도 한 바퀴 범위의
같은 방향 번호로 바꾼다. `mod`는 나머지를 취하는 연산이다.

### CORDIC과 고정소수점

좌표를 회전시키려면 각도의 cos · sin 값이 필요하다. **CORDIC(Coordinate Rotation Digital Computer)**은
작은 회전을 여러 번 이어 붙여 이 값을 구하는 방법이다. 이번 반복형 회로는 같은 덧셈 · 시프트 회로를
여러 클럭에 나눠 쓴다. 이벤트마다 새로 구할 필요가 없어 회로를 크게 펼치지 않아도 된다.

cos · sin은 회전 모드 CORDIC으로 프레임마다 한 번 구한다. 프레임 간격은 약 776 µs라서 반복형 CORDIC 하나로
충분하다. 출력 C · S는 부호 16비트, 소수 14비트(1.0 = 16384)다.

이것이 **고정소수점** 표현이다. 예를 들어 실제 값 0.5를 정수 8,192로 저장하고, 계산할 때 이 배율을
기억한다. 실수 연산 장치 없이 정수 곱셈 · 덧셈으로 처리할 수 있다. 아래 표는 RTL과 SW가 같은 값을
내도록 정한 정확한 연산 규칙이다. 원리를 이해할 때는 “프레임 각도 하나를 C · S 두 정수로 바꾼다”는 점을 알면 된다.

| 단계 | 정수 연산 |
|---|---|
| 사분면 | q = φ[15:14], 사분면 안 각도 r = φ[13:0] |
| 시작 | z = (r << 3) − 65536. 보호 비트 3개를 붙이고 45°를 빼서 [−45°, 45°)로 옮긴다. x = y = X0 = 56281(45° 방향, CORDIC 이득의 역수 × 2^17 / √2) |
| 반복 i = 0 ~ 15 | d = (z ≥ 0) ? +1 : −1. x ← x − d·(y >>> i), y ← y + d·(x >>> i), z ← z − d·ATAN[i]. x · y는 이전 값으로 동시에 바꾼다 |
| ATAN[i] | 65536 38688 20442 10377 5208 2607 1304 652 326 163 81 41 20 10 5 3 |
| 마무리 | x ← (x + 4) >>> 3, y ← (y + 4) >>> 3. q = 0 · 1 · 2 · 3이면 (C, S) = (x, y) · (−y, x) · (−x, −y) · (y, −x) |

`>>>`는 산술 시프트(내림)다. x · y는 부호 19비트, z는 부호 18비트면 넘치지 않는다. 위상 65,536개 전부에서
실수 cos · sin과의 차이는 1.92 LSB 이하다.

## 3.3 이벤트마다: 월드 칸

### 숫자 하나로 따라가기

장면 1의 회전 중심과 메모리 설정(3.4 · 3.5절)을 쓰고, 설명을 위해 중심보다 오른쪽으로 16 px 떨어진
픽셀 `(549, 418)`에 이벤트 하나가 났다고 하자. 아래는 `golden.py`의 정수 연산으로도 같은 결과가 나오는 예제다.

| 적용할 위상 | 회전 중심을 뺀 좌표 | 회전 후 중심 기준 좌표 | 월드 픽셀 좌표 | 저장할 월드 칸 |
|---|---|---|---|---|
| 0 (0°) | (16, 0) | (16, 0) | (720, 704) | (180, 176) |
| 16,384 (90°) | (16, 0) | (0, 16) | (704, 720) | (176, 180) |

월드 칸 하나가 여러 픽셀 길이를 묶으므로 마지막에 좌표를 칸 크기로 나눠 내림한다.
이 예제는 **같은 입력 점에 보정 각도가 다르면 출력 주소가 달라진다**는 계산 예제다.
실제 정지 물체를 서로 다른 시점에 볼 때는 입력 픽셀과 보정 각도가 함께 바뀌어 같은 출력 위치로 모여야 한다.

### RTL과 맞출 정수 계산 규칙

    dx = x − cx,  dy = y − cy                  부호 11비트
    u  = C·dx − S·dy + WC·2^14                 부호 27비트
    v  = S·dx + C·dy + WC·2^14
    wx = u >>> 16,  wy = v >>> 16             16 = 소수 14비트 + 칸 크기 2비트

(cx, cy)는 회전 중심(정수 px), WC는 704 px다. 0 ≤ wx < 352이고 0 ≤ wy < 352이며 칸 (wx, wy)가 저장 영역
(3.4절)에 들면 그 칸을 1 올리고, 아니면 그 이벤트를 버린다. 곱 하나는 부호 26비트 안에 들고, 두 곱과 WC·2^14를
더해도 부호 27비트를 넘지 않는다.

`u`, `v`는 소수점 배율이 아직 남아 있는 중간 좌표이고, `wx`, `wy`가 최종 메모리 칸 번호다.
`>>> 16`은 소수점 배율을 없애는 일과 칸 크기로 나누는 일을 한 번의 시프트로 한다.
음수도 부호를 유지해 아래 정수로 내리므로, 0 쪽으로 잘라 버리는 나눗셈과 혼동하지 않는다.

칸을 1씩 올리는 포화 덧셈은 순서를 바꿔도 결과가 같다. 그래서 RTL은 이벤트를 어떤 순서로, 몇 개씩 묶어
처리하든 마지막 메모리가 골든 모델과 같아야 한다.

## 3.4 월드 메모리

### 한 칸에는 무엇이 들어 있나

월드 메모리는 **같은 위치로 변환된 이벤트가 몇 번 왔는지 세는 표**다. 처음에는 모든 칸이 0이고,
이벤트가 들어온 칸에 1을 더한다. 밝아짐과 어두워짐을 따로 저장하거나 서로 빼지 않는다.
시각이나 이벤트 목록도 칸 안에 남기지 않는다.

예를 들어 한 칸에 ON 이벤트 두 개와 OFF 이벤트 한 개가 들어오면 값은 3이다. 이 값이 크다는 것은
그 위치에 변화 기록이 많이 모였다는 뜻이지, 실제 물체가 밝다거나 물체가 세 개라는 뜻은 아니다.
결과 그림은 이 숫자 표를 진하기로 표시한 것이다.

**포화 카운터**는 담을 수 있는 최댓값에 이르면 더는 증가하지 않는 카운터다. 가득 찼을 때 0으로 돌아가는
넘침을 막는다. 예를 들어 최댓값보다 두 번 더 들어와도 최댓값을 유지한다. 이 때문에 최종 메모리 합이
전체 입력 이벤트 수보다 작을 수 있다. 범위 밖이라 버린 이벤트와 포화로 더하지 못한 이벤트는 원인이 다르다.

### 좌표 범위와 실제 저장 용량

| 항목 | 값 |
|---|---|
| 크기 N × M | 352 × 352칸 좌표계. 칸이 4 px라 한 변이 1408 px |
| 저장 영역 | 월드 중심에서 반지름 696 px인 원에 걸치는 칸. 뱅크 16개가 표 하나를 같이 쓰므로 뱅크마다 6,132칸, 모두 98,112칸 |
| 칸 크기 | 4 × 4 px |
| 칸 내용 | 이벤트 수. 13비트 포화 카운터(8191에서 멈춘다). 극성은 가리지 않는다 |
| 같은 칸에 다시 쓸 때 | 더한다 |
| 용량 | 1,275,456비트(약 156 KiB) |

`352 × 352`는 주소를 부를 때 쓰는 정사각형 격자다. 모든 격자 칸을 실제 SRAM에 두는 것은 아니다.
센서 화면을 회전시키면 도달 가능한 범위가 원 모양이 되므로, 저장 영역 표에 든 칸만 물리 메모리에 둔다.
뱅크마다 같은 표를 쓰기 위해 원에 걸치는 영역을 뱅크 단위로 합쳐 잡는다. 따라서 완벽한 원 안의 칸 수를
단순히 센 것과 실제 저장 칸 수는 다를 수 있다. 표 밖의 칸을 읽으면 0을 돌려준다.

위 용량은 **실제로 저장하는 칸 수 × 칸당 비트 수**다. SRAM macro는 정해진 크기로 만들기 때문에
macro를 조합하면 남는 주소가 조금 생긴다. 그래서 정보 비트 수와 칩에서 차지하는 SRAM 면적은 서로 다른 값이다.
칸 크기의 px는 이 영상 좌표계의 길이 단위이며, 실제 공간에서 몇 mm인지를 뜻하지 않는다.

크기와 칸 비트 수의 근거는 [설계 근거 5절](../reports/01_설계_근거.md#5-칸-비트)이다.
칸 크기를 1 · 2 · 8 px와 비교한 결과와, 이벤트를 거르지 않고 모두 세는 근거(노이즈 · 핫픽셀)는
[설계 근거 4절](../reports/01_설계_근거.md#4-월드-칸-크기와-노이즈-거르기)에 있다.
처음에는 정사각형 전체(123,904칸)를 14비트로 두었다. 칸 내용을 13비트로 줄여도 막대 측정이 같고, roll이 닿는 곳은
원 안뿐이라 원에 걸치는 칸만 두었다([설계 근거 6절](../reports/01_설계_근거.md#6-저장-영역) 3 · 4절). 원의 반지름
696 px는 뱅크마다 macro 조합이 같은 가장 큰 값이고, 장면 1에서 회전 중심이 가장 먼 센서 모서리까지 677.4 px라 모든
이벤트를 담는다. 저장 영역 표는 `software/golden_develop/region_check.py`가 만들고, 골든 모델(`golden.py`의 `stored_mask`)과
RTL(`wl_region_map`)이 같은 표를 쓴다. 용량은 14비트 정사각형(1,734,656비트)의 73.5 %다.
SRAM 컴파일러가 없으므로 이 메모리는 지연 · 면적을 가정한 모델로 둔다([1장 1.2절](01_프로젝트_개요.md#12-주최-측이-정한-조건)).

## 3.5 장면 1 설정값

장면 1(`2026-09-22-16-42-44`)에서 SW가 추정한 값이다. 추정 방법은 [설계 근거 2절](../reports/01_설계_근거.md#2-회전-중심과-회전각-추적)에 있다.
칩은 프레임마다 위상 φ를 입력으로 받는다. 실제 시스템에서는 자이로 등의 측정값을 위상으로 바꾸는 외부 처리가
필요하고, 여기서는 이 SW 추정이 그 자리를 채운다.

중심 값은 한 녹화를 처리하는 동안 고정한다. 장면을 바꾸면 중심 입력도 그 장면에 맞게 줄 수 있지만,
현재 회로에서 프레임마다 중심을 바꾸는 기능을 구현한 것은 아니다.

## 3.6 RTL 테스트벤치 벡터

**테스트벤치**는 회로 밖에서 입력을 보내고 결과를 검사하는 시험용 코드다. **시험 벡터**는 그 코드가 읽을
입력값과 기댓값 파일이다. 아래 파일들을 묶어 두면 SW와 RTL에 같은 구간 · 같은 각도를 정확히 넣을 수 있다.
`hex`는 값을 16진수로 한 줄씩 적은 텍스트 파일이라는 뜻이다.

`golden.py`가 프레임 f0 ~ f1−1을 잘라 아래 파일을 만든다. 기본 구간은 프레임 500 ~ 539이고, 프레임 카운터가
4 뛰는 514 앞 자리를 품는다.

| 파일 | 내용 |
|---|---|
| `words.hex` | 원시 32비트 워드, 한 줄에 하나(16진 8자리). 프레임 f0−1을 닫는 끝 표지부터 프레임 f1−1을 닫는 끝 표지까지 |
| `phase.hex` | 프레임 f0 ~ f1−1의 위상 φ(16진 4자리). k번째 프레임의 이벤트는 k번째 위상을 쓴다 |
| `trig.hex` | 같은 프레임의 CORDIC 출력 "C S"(각각 16비트 2의 보수, 16진 4자리) |
| `cordic_all.hex` | 위상 0 ~ 65,535 전부의 CORDIC 출력 "C S". CORDIC 단독 전수 시험용 |
| `expected.hex` | 빈 메모리에서 이 프레임들을 누적한 메모리. 주소 0부터 123,903까지 한 줄에 한 칸(16진) |
| `params.txt` | 위 상수들과 프레임 · 워드 · 이벤트 수, 메모리 합과 최댓값 |

프레임 경계는 [2장 2.1절](02_입력_형식.md#21-파일-구조)처럼 카운터가 바로 앞 끝 표지와 다른 끝 표지에서만
센다. `words.hex`는 끝 표지로 시작하고 그 앞에 이벤트가 없으므로, RTL은 리셋 뒤 첫 끝 표지에서 카운터만
기억한다([4장 4.4절](04_RTL_구조.md#44-프레임-경계와-각도-바꾸기)). f0 = 0이면 `words.hex`는 파일 첫 워드부터다.

`expected.hex`는 시험에서 읽을 **정사각형 전체 주소 공간**을 적으므로, 실제 SRAM에 저장하지 않는 칸도
0으로 포함한다. `world.npy`는 녹화 전체 결과이고 기본 `vectors/expected.hex`는 잘라 낸 구간의 결과다.
입력 구간이 다르므로 두 메모리의 값이 같아야 하는 것은 아니다. 실행 예제는
[7장](07_파일_안내와_재현.md)에 있다.
