## 1. `cin_en` 에 `~r_ack` 누락 — 설계 결함

### 증상

8채널 동시 발화 시험에서 **8건 중 5건만 배출**되었다. 순차 시험(한 번에 하나씩)은 통과했다.

- 소스는 전부 ack를 받고 정상 종료 → **deadlock이 아니라 acked-then-dropped, 즉 silent loss**
- 손실이 root 중재에서 **패배한 서브트리에만** 집중 (좌 1/4, 우 4/4)
- → **backpressure 하에서만 발생**

### 진단 과정

처음 두 가설이 모두 틀렸다.

| 가설 | 조치 | 결과 |
|---|---|---|
| ① mutex 핸드오버 창 부족 | `GNT_GAP` 증가 | **처방 자체가 틀림** — behavioural `delay_chain` 은 lumped inertial delay이므로 50 ps 펄스를 100 ps 지연에 넣으면 창이 넓어지는 게 아니라 **삼켜진다** |
| ② 델타 사이클 경합 | C-element에 20 ps 지연 부여 | **결과 무변화** → 경합이 아니라 결정론적 논리 문제 |

추론으로 두 번 실패한 뒤, **7개 노드 전부에 계측**을 넣었다.

```
cap = posedge cin    (노드가 주소를 래치)
fwd = posedge r_req  (부모에게 전달)
```

### 결과 — 즉시 국소화

```
PHASE 2 (8 동시)          PHASE 3 (Poisson)
lvl0 : 2/2 2/2 2/2 2/2    lvl0 합계 10003  = accepted
lvl1 : 4/4 4/4            lvl1 합계 10003
root : 5/5   ← 8건 중 5건  root       9975  ← 28건 증발
```

`cap > fwd` 인 노드가 **하나도 없었다.** 즉 어떤 노드도 래치 후 떨어뜨리지 않았고, **root가 상승엣지 자체를 만들지 못했다.**

### 원인

`cin = C(granted, ~cout)` 에서 **`cout = 0` 이면서 `r_ack = 1` 인 구간**이 존재한다.

```
cout 하강 → r_req 하강(REQ_DLY) → 부모 인지 → r_ack 하강
      └────── cout=0, r_ack=1 ──────┘   ← 이 구간이 구멍
```

이 구간에 새 자식이 grant를 받으면 `~cout = 1` 이므로 `cin = C(1,1) = 1` 이 되어, **이전 4-phase가 return-to-zero 되지 않은 채널에 새 이벤트가 admit**된다. 이후 그 자식이 요청을 내려도 `cin = C(0, ~cout=1) = hold(1)` 이라 cin이 다시 떨어지지 못하고, 다음 자식은 `l_ack = g & cin = 1` 을 즉시 받아 사라진다.

**손실이 전량 root에 몰린 이유**: root의 acknowledge 왕복이 가장 길어(matched delay + sink 왕복) **구멍이 가장 넓다.** 하위 단은 왕복이 짧아 구멍이 열리지 않는다.

### 수정

```verilog
wire cin_en = cout_n & r_ack_n;   // 출력 채널이 "완전히" idle 일 때만 입력 허용
```

입출력 중첩이 약간 줄지만 핵심 semi-decoupled 성질은 유지된다 — 자식의 4-phase는 여전히 `r_ack` 를 기다리지 않고 완료된다.

### 결과

전 단계 통과. 보존이 정확히 성립했다.

```
lvl0 합계 10001 = lvl1 합계 10001 = root 10001 = accepted
내부 손실 0, in-flight 0, 주소 오류 0
```

오염됐던 latency 통계도 정상화되었다 (285 ns → 1.60 ns).

### 방법론적 의의

> 이 결함은 **acknowledge 왕복이 가장 긴 노드에서만** 드러난다. 순차 발화 시험은 통과했고, 소규모·저부하 시뮬레이션으로는 놓친다. **노드별 계측을 넣기 전까지 세 번의 추론이 모두 빗나갔다.**

## 2. mutex가 동시 도착을 해소하지 못함 — 준안정성

### 증상

합성 대상 경로(structural)로 처음 전환하자 동시 발화 시험이 **8건 중 1건**만 배출했다. 동시에 root가 ~1.92 ns 주기로 자유발진했고, **모든 오류가 채널 0을 가리켰다.**

### 진단

단계를 분리한 것이 결정적이었다.

| 단계 | 결과 | 의미 |
|---|---|---|
| 0 IDLE (자극 없음) | PASS | 리셋 직후 발진이 아님 |
| 1 DIRECTED (하나씩) | PASS | **tie가 발생하지 않으므로 통과** |
| 2 BURST (동시) | FAIL | **모든 mutex가 정확한 tie를 맞음** |

그리고 **오류 주소가 전부 채널 0**이라는 점이 원인을 확정했다.

### 원인

`r1` 과 `r2` 가 같은 델타에 도착하면 cross-coupled NAND 쌍이 완전 대칭이 된다.

```
n1 = ~(1 & n2)  →  2·TPD 후 0
n2 = ~(1 & n1)  →  2·TPD 후 0      (지연이 동일)
둘이 함께 0 → 함께 1 → 주기 4·TPD 로 무한 진동, 래치되지 않음
```

`n1 == n2` 인 동안 **두 grant가 모두 0**이다 (`g1 = ~n1 & n2`, `g2 = ~n2 & n1`). 따라서 모든 노드가 `sel = 0` 을 내보내 **주소가 all-zeros로 축퇴**되고, root는 sink를 상대로 채널 0을 무한 방출한다.

### 수정

한쪽 NAND에 **1 ps 소자 mismatch**를 부여해 대칭을 깬다. 핸드오버 창(40 ps)보다 40배 작아 타이밍 마진에 영향이 없다.

```verilog
nand #(2.0*TPD_NS)               u_n1 (n1, r1, n2);
nand #(2.0*TPD_NS + MISMATCH_NS) u_n2 (n2, r2, n1);
```

### 의의 — 이것은 버그가 아니라 결과다

> 실리콘에서는 소자 mismatch와 열잡음이 준안정 창 안에서 대칭을 깬다. 순수 디지털 시뮬레이터에는 그것이 없으므로 영원히 해소하지 못한다.
>
> **즉 이 현상 자체가 "표준셀 합성으로는 arbiter를 보장할 수 없다"의 직접 증거다.** 준안정성은 모델링 불편이 아니라 회로의 물리적 성질이며, 실제 셀에는 아날로그 준안정 필터가 필요하다.

**부수 효과**: 이 수정으로 tie 승자가 **결정적**이 된다. 이것이 고정 mismatch가 실리콘에서 하는 일과 같으므로, behavioural(LFSR 무작위)과 structural(고정 mismatch)을 비교하면 **tie-break 정책의 양 극단을 정량적으로 괄호칠 수 있다.**

| | 고정 mismatch | LFSR |
|---|---|---|
| 평균 rank 산포 | **63.00** (최대) | **3.24** (잡음 수준) |
| 버스트 latency 범위 | 3.1 ~ 120.3 ns | 58.7 ~ 64.4 ns |

이 대비가 곧 설계보고서 §4.1의 근거가 되었다.

## 3. 대량 요청 변경 시 arbiter 정착 — 설계 요구사항

### 증상

제안 구조에서 주소 오류가 발생했고, **오류 수가 스냅샷 비율과 정확히 연동**했다.

| 스냅샷 비율 | 오류 |
|---|---|
| 0% | 없음 |
| 1.1% | 첫 발생 |
| 35%+ | 다수 |

### 원인

`eff_req` 가 `px_req ↔ held` 로 **한꺼번에** 바뀌면 두 arbiter tree가 전체 재정착한다. 그 과정에서 grant가 글리치하고 `granted = |col_g` 가 흔들려 **가짜 상승엣지**로 쓰레기 주소를 래치한다.

베이스라인은 요청이 한 픽셀씩 바뀌므로 국소 재정착만 일어나 이 문제가 없다.

### 수정

전환 구간 동안 출력단을 동결한다.

```verilog
wire granted = (|col_g) & settle_n;
```

`T_SETTLE` 은 `row tree → column lines → column tree` 직렬 경로를 넘어야 하며, 기본 파라미터에서 약 0.5 ns다. 파라미터로 두어 마진을 스윕할 수 있게 했다.

### 결과 — 부분 해결

주소 정합성 계측이 전 구간 0이 되고 오류가 약 4배 줄었다. **그러나 완전히 사라지지는 않았다.** 남은 원인은 정착 게이트의 폭이 아니라 **게이트를 거는 시점 판정**이었고, §9에서 규명했다.

### 의의

> **모델링 편의가 아니라 실제 설계 제약이다.** 요청 집합이 대량으로 바뀌면 arbiter는 정착 시간이 필요하고, 그 전에는 주소가 유효하지 않다.

## 4~6. 합성 대상 경로 착수 전 사전 점검

structural 경로를 처음 돌리기 전에 코드를 점검해 세 가지를 미리 고쳤다. **고치지 않았다면 아예 동작하지 않았을 것들이다.**

| # | 파일 | 결함 | 수정 |
|---|---|---|---|
| 4 | `c_element.v` | **X 전파.** 피드백을 리셋 게이트 **앞** 노드에서 따서 상태 노드가 리셋되지 않음. `a=0` 이면 루프가 `z = b & z` 로 축퇴돼 시간 0부터 X를 유지하고, 리셋 해제 순간 X가 요청 경로 전체로 번진다 | 피드백을 리셋 게이트 **뒤**(`z`)에서 따도록 변경 |
| 5 | `delay_chain.v` | 버퍼가 zero-delay라 체인이 **투명**. `REQ_DLY` 가 시뮬레이션에서 무효가 되어 bundled-data 마진이 **조용히 미검증** 상태가 된다 | 단당 지연 부여 |
| 6 | `mutex.v` | structural 핸드오버 창이 하드코딩 20 ps인데 C-element 응답도 20 ps → **마진 0** | `TPD_NS` 파라미터화. 창 = 2·TPD(structural) / 2.5·TPD(behavioural), 기본 20 ps에서 2~2.5배 마진 |

**6번의 창 폭은 게이트 지연에서 직접 유도했다** (`r1` 하강 기준, nand=2t, not/and=t):

```
n1 상승 2t → n1_b 하강 3t → g1 하강 4t
n2 하강 4t → n2_b 상승 5t → g2 상승 6t
창 = 6t − 4t = 2t
```

## 7. 계측 큐 미리셋 — latency 통계 오염

### 증상

`worst latency = 20,680 ns` 가 보고되었으나, 평균은 351 ns였고 최소는 1.38 ns였다. **부하 10%에서 물리적으로 불가능한 값**이다.

### 원인

단계 전환 시 이벤트 카운터는 리셋하면서 **birth-time 큐 포인터를 리셋하지 않았다.** 앞 단계에서 잃은 이벤트가 큐를 영구히 어긋나게 만들어, 이후 모든 latency가 **N개 전 이벤트의 발생시각** 기준으로 측정되었다.

**결정적 단서**: `20,680 ns` 가 앞 단계 타임아웃(20 µs)과 거의 일치했다. 앞 단계에서 남은 죽은 발생시각이 pop된 것이다.

### 수정

단계 전환 시 배출 완료 대기 + 큐 포인터 리셋. 추가로 **in-flight 정합성 검사**를 넣어 통계가 스스로 유효성을 신고하게 했다.

```
accepted − completed > 노드 수  →  "SILENT LOSS, latency 무효" 자동 출력
```

### 의의

> 계측 코드의 결함은 **설계가 정상일 때도 잘못된 결론을 만든다.** 이후 모든 지표에 자기검증(보존 검사, 자기일관성 검사)을 넣었다.

## 8. 오류 출력 무제한 — 로그 소실

멈춘 노드가 ~2 ns마다 주소를 방출하자 동일한 오류가 **104,167줄** 출력되어, 빌드 배너와 단계별 판정이 콘솔 스크롤백 밖으로 밀려났다. 진단에 필요한 정보가 전부 사라진 것이다.

출력 상한 20줄로 제한하고 카운트는 정확히 유지하도록 수정했다.

## 9. 재구성 시점 판정 오류 — `cin == 0`은 "유휴"를 뜻하지 않는다

### 증상

제안 구조에서 배출된 주소 중 약 **0.02 %**(20만 이벤트 중 38건)가 `output claims px N with no pending event` 로 보고되었다. 베이스라인(스냅샷 비활성)은 오류 0이다.

### 진단 — 네 번의 시도, 세 번의 반증

먼저 세 가지 계측을 넣었으나 **전부 0**이었다.

| 계측 | 의미 | 결과 |
|---|---|---|
| `ORPH` (ack > 배출) | ack만 받고 배출 안 됨 | 0 |
| `PHAN` (배출 > ack) | ack 없이 배출된 주소 | 0 |
| `SPUR` (대기 없는 픽셀에 ack) | 유령 acknowledge | 0 |

그러나 이 셋에는 사각지대가 있었다. **오류가 난 배출은 완료 카운터를 증가시키지 않으므로**, ack 없는 배출이 있어도 `PHAN`은 0으로 나온다. 그래서 배출 경로 전체를 세는 계측으로 바꿨다.

```
posedge cin      주소를 래치
posedge px_ack   grant된 픽셀을 acknowledge
posedge out_req  주소를 배출
```

결과가 결정적이었다.

```
베이스라인 :  n_cin = n_ack = n_out,  오류 0
제안 구조  :  n_cin = n_ack + 오류 수,  n_out = n_cin
```

**`cin`이 어서트되는데 어떤 픽셀도 acknowledge되지 않았다.** `px_ack = row_g & col_g & cin` 이므로 그 순간 행 또는 열 grant가 0이다.

여기서 세 번 잘못 짚었다.

| 시도 | 가설 | 반증 |
|---|---|---|
| 1 | 행/열 grant의 전파 시차 | 수정 후 결과가 **바이트 단위로 동일** — 무영향 |
| 2 | 테스트벤치가 엣지를 놓침 | 독립 카운터가 **일치** — 계측 무죄 |
| 3 | 스냅샷 회수가 너무 이름 | 회수를 지연시키자 오류 **증가**(10 → 15) |

### 데이터가 처음부터 말하고 있던 것

오류를 스냅샷 활성 시간과 나란히 놓자 패턴이 드러났다.

| 스냅샷 비율 | 0.1 % | 1.2 % | 9.7 % | 37 % | 81 % | **96 %** | **98 %** | **98 %** |
|---|---|---|---|---|---|---|---|---|
| 오류 | 0 | 1 | 2 | 3 | 4 | **0** | **0** | **0** |

**스냅샷이 거의 상시 걸린 구간에서 오류가 0이다.** 오류는 스냅샷 *시간*이 아니라 **모드 전환 횟수**를 따랐다. 즉 정상 배출 중이 아니라 **전환 경계**의 문제였다. 이 사실을 먼저 봤다면 세 번의 헛수고를 피할 수 있었다.

### 상태 직접 캡처 — 원인 확정

추론을 멈추고, 잘못된 래치가 일어나는 순간의 상태를 그대로 찍었다. **8건 전부 동일했다.**

```
row_g=0 | settle=0 | hold=1 | snap=0 | cout=0 out_ack=0 | held == px_req
```

세 가지가 즉시 확정되었다.

1. **정착 게이트가 어서트된 상태**(`settle=0`)인데도 `cin`이 떴다. 게이트가 `granted`를 0으로 만들고 있었는데도.
2. `held`와 `px_req`가 **정확히 같다** — 스냅샷을 뜬 바로 그 순간, 즉 **진입 경계**다.
3. 행 grant가 0이다.

### 원인

C-element는 **입력에서 래치하고 유지**한다. `granted`와 입력 인에이블이 아무리 짧게라도 겹치면 내부 상태가 서고, 출력은 한 전파지연 뒤에 **반드시** 어서트된다 — 그 사이 `granted`가 0으로 떨어져도 `C(0,1) = hold` 이므로 취소되지 않는다.

```
granted 어서트  →  내부 래치 = 1        (아직 전파지연 안 지남)
                   cin 은 여전히 0
제어부: "cin == 0 이므로 유휴"  →  정착 게이트 하강, 스냅샷, 입력 집합 교체
                   grant 이동
+전파지연        →  cin 어서트. 가리킬 픽셀이 없음 → acknowledge 0건
```

**`cin == 0`은 "트랜잭션이 없다"가 아니라 "C-element 출력이 아직 안 떴다"이다.** 제어부가 그 창에서 재구성을 시작했다.

### 수정

대기 조건과 순서를 함께 고쳤다.

```
① 정착 게이트를 먼저 내려 새 트랜잭션을 차단
② C-element 전파지연만큼 대기 — 이미 확정된 트랜잭션이 해소되도록
③ cin 과 cout 이 모두 0이 될 때까지 대기 — 그 트랜잭션이 완전히 종료
④ 그제서야 입력 집합 변경
```

핵심은 **입력 집합 변경을 정착 게이트 하강과 같은 시점에 두지 않는 것**이다.

### 결과

잘못된 래치 0건, 배출 오류 0건, 전 단계 통과. 세 계수가 전 구간에서 일치한다.

```
n_cin = n_ack = n_out,  오류 0
```

**대가가 드러났다.** 전환마다 출력단을 정지시키므로 용량이 538.4 → 519.1 Meps(**−3.6 %**)로 줄고, 전환이 잦은 중간 부하에서 손실이 늘었다. 수정 전 수치(−0.4 %)는 결함이 있는 상태의 값이었다.

### 의의

> **비동기 회로에서 중재 입력 집합을 재구성하려면 출력단이 실제로 정지해야 하며, "정지"의 판정에 제어 자신의 전파지연을 포함해야 한다.**
>
> 그리고 이것이 **경계 스냅샷 방식이 지불하는 숨은 비용**이다. 픽셀 내부에 이벤트 메모리를 두면 요청 하강이 픽셀을 거치면서 이 창이 자연히 닫힌다. 디지털 블록 안으로 스냅샷을 옮기면 그 여유가 사라지고, 정착 시퀀스를 명시적으로 설계해야 한다.

## 10. 검증 방법론에서 얻은 원칙

이 과정에서 반복적으로 확인된 것들이다.

1. **추론보다 계측이 빠르다.** 결함 1과 2에서 각각 두 번, 한 번 가설이 빗나갔고, 계측을 넣은 직후 원인이 확정되었다.
2. **단계를 분리하면 원인이 좁혀진다.** IDLE / 순차 / 동시 를 나눈 덕분에 "tie에서만 실패"가 즉시 드러났다.
3. **오류의 패턴이 원인을 지목한다.** 모든 오류가 채널 0을 가리킨 것이 준안정성 진단의 결정적 단서였다.
4. **소규모·저부하 시험은 통과시킨다.** 결함 1은 acknowledge 왕복이 가장 긴 노드에서만, 결함 2는 동시 도착에서만 나타났다.
5. **계측 자체를 검증해야 한다.** 결함 7은 설계가 정상일 때도 틀린 숫자를 만들었다.
6. **집계는 사각지대를 만든다.** `ORPH`/`PHAN`/`SPUR` 세 계측이 모두 0이었지만 결함은 존재했다 — 오류가 난 배출이 완료 카운터에 잡히지 않아 비교가 성립하지 않았다. 경로 전체를 세는 계측으로 바꾸고 나서야 드러났다.
7. **집계가 막히면 상태를 찍어라.** 세 번의 가설이 빗나간 뒤, 실패 순간의 신호 상태를 그대로 출력하자 8건이 전부 같은 패턴이었고 원인이 즉시 확정되었다.
8. **닫힌 형태 예측과 대조하라.** scan 구조의 σ = T_frame/√12, mean = T_frame/2, worst = 2·T_frame, 손실률 = 1−(1−e^−ρ)/ρ 네 가지가 모두 실측과 일치한 것이 모델 타당성의 독립 근거가 되었다.
